# План реализации: Diet Debugger

## Блок 1: Фундамент

### 1.1 Структура solution
**Что:** Создать .NET solution с layered архитектурой: `DietDebugger.Api`, `DietDebugger.Application`, `DietDebugger.Domain`, `DietDebugger.Infrastructure`. Настроить project references, общие NuGet-пакеты (EF Core, MediatR, FluentValidation).
**Принятие:** `dotnet build` проходит; граф зависимостей верный (Api → Application → Domain; Infrastructure → Application).
**Примечания:** Domain — без зависимостей от EF Core. Application владеет интерфейсами; Infrastructure их реализует.

### 1.2 PostgreSQL + EF Core
**Что:** Добавить EF Core с провайдером Npgsql в Infrastructure. Настроить `AppDbContext`. Создать и применить начальную миграцию (пустую — только проверка подключения).
**Принятие:** `dotnet ef migrations add Initial` успешно; `dotnet ef database update` создаёт БД; health check endpoint возвращает 200 с подтверждением подключения к БД.
**Примечания:** Connection string через env переменную / `appsettings.Development.json`.

### 1.3 User entity + JWT авторизация
**Что:** Создать сущность `User` (Id, Email, PasswordHash, CreatedAt). Реализовать: регистрацию (`POST /auth/register`), вход (`POST /auth/login`), refresh (`POST /auth/refresh`) с парой JWT access + refresh токен.
**Принятие:** Register → Login возвращает JWT; защищённый endpoint возвращает 401 без токена, 200 с валидным; refresh выдаёт новый access token.
**Примечания:** `BCrypt.Net` для хэширования паролей. Refresh токены в БД с expiry.

### 1.4 React + Vite scaffold
**Что:** Создать React + Vite проект (`/client`). Настроить: React Router v6 (роуты: `/`, `/day`, `/week`, `/analytics`, `/profile`, `/auth`), Axios с JWT interceptor (auto-attach, auto-refresh на 401), защищённый роут, глобальный toast context (заглушка).
**Принятие:** Приложение запускается; неаутентифицированный пользователь редиректится на `/auth`; аутентифицированный попадает на `/day`; toast context рендерится без ошибок.
**Примечания:** Использовать `pnpm`. UI библиотека не нужна пока — CSS modules достаточно.

## Блок 2: Ядро логирования еды

### 2.1 Meal entity + миграция
**Что:** Создать сущность `Meal`: `Id`, `UserId`, `LoggedAt`, `Calories`, `ProteinG`, `FatG`, `CarbsG`, `Ingredients` (JSON), `PortionEstimate`, `ConfidenceScore`, `Source` (enum: Photo/Text/Manual), `Notes`. Миграция + конфиг DbContext.
**Принятие:** Миграция применяется чисто; EF может сохранить и прочитать запись `Meal`.

### 2.2 FoodVisionAgent интерфейс + реализация
**Что:** Определить `IFoodVisionAgent` в Application: `Task<FoodVisionResult> AnalyzeAsync(FoodVisionInput input)` — вход: байты изображения или текст. Реализовать через реальную vision-модель. Возврат: список ингредиентов, калории, БЖУ, оценка порции, уверенность (0–1).
**Принятие:** Интеграционный тест: отправить реальное фото → получить структурированный результат с calories > 0 и confidence score.
**Примечания:** Таймаут вызова API — 10с. Логировать prompt + response. Модель выбирается через конфиг.

### 2.3 Async API анализа блюда
**Что:** `POST /meals/analyze` — принимает фото или текст, ставит задачу в очередь, возвращает `jobId`. `GET /meals/analyze/{jobId}` — возвращает статус (`pending` / `ready` / `failed`) и результат когда готово. Состояние задачи хранится в БД (`AnalysisJob` таблица).
**Принятие:** Загрузить фото → поллить до `ready` → получить структурированный результат; поллить после сбоя → получить `failed` с сообщением об ошибке.
**Примечания:** Простой in-process background worker (IHostedService queue) для MVP.

### 2.4 Meal CRUD API
**Что:** `POST /meals` (сохранить подтверждённый приём), `GET /meals/{id}`, `PUT /meals/{id}` (редактировать), `DELETE /meals/{id}` (hard delete), `GET /meals?date=YYYY-MM-DD` (список за день). Всё в контексте аутентифицированного пользователя.
**Принятие:** Полный CRUD работает; пользователь не может обращаться к чужим блюдам (403); фильтр по дате возвращает корректное подмножество.

### 2.5 MealFeedbackAgent (Level 1)
**Что:** Реализовать rule-based `MealFeedbackAgent` в Application. Запускается синхронно после сохранения блюда. Вход: сохранённое блюдо + текущие итоги дня + профиль (если есть). Выход: статус (`ok`/`warning`/`issue`) + 1–2 строки инсайта.
**Принятие:** Unit-тесты покрывают все правила; сохранение жирного блюда → `warning` + текст инсайта; сбалансированного → `ok`.
**Примечания:** LLM не используется. При отсутствии профиля — общие пороги (2000 ккал/день).

### 2.6 Frontend: флоу добавления блюда
**Что:** FAB "+" на вкладке "День" → bottom sheet с тремя вариантами: Сфотографировать (file input `capture="camera"`), Выбрать из галереи (file input), Ввести текстом (textarea). При отправке: вызов `POST /meals/analyze`, показ спиннера, поллинг `GET /meals/analyze/{jobId}` каждые 1.5с до готовности или ошибки.
**Принятие:** Полный флоу работает на мобильном браузере (iOS Safari + Android Chrome). Спиннер показывается. При ошибке — сообщение.

### 2.7 Frontend: экран результата + редактирование
**Что:** После завершения анализа: экран с редактируемым списком ингредиентов, калориями, БЖУ, бейджем уверенности. Если confidence < 0.7: жёлтый баннер "Мы не уверены — проверь или сфоткай снова". Редактируемые поля. Кнопка "Сохранить" → `POST /meals`. После сохранения: карточка MealFeedback (статус + инсайт). Кнопка "Назад" — отмена без сохранения.
**Принятие:** Результат с низкой уверенностью показывает баннер; правки отражаются в сохранённом блюде; карточка фидбэка появляется.

## Блок 3: Экран дня

### 3.1 DailySummary entity + API
**Что:** Создать `DailySummary`: `UserId`, `Date`, `TotalCalories`, `TotalProteinG`, `TotalFatG`, `TotalCarbsG`, `Insights` (JSON), `GeneratedAt`, `IsStale` (bool). `GET /daily-summary?date=` — возвращает summary или 404. `POST /daily-summary/invalidate?date=` — помечает как устаревший.
**Принятие:** API возвращает 404 для дня без summary; инвалидация устанавливает `IsStale = true`.

### 3.2 DailySummaryAgent
**Что:** Реализовать `DailySummaryAgent` (Level 2, LLM). Вход: список блюд за день + профиль/цели. Выход: массив инсайтов (2–4 строки). Запускается при GET daily-summary когда summary отсутствует или устарел.
**Принятие:** Интеграционный тест: сохранить 3 блюда → вызвать GET daily-summary → массив с 2–4 непустыми строками; второй вызов возвращает кэш (новый LLM-вызов не происходит).
**Примечания:** Мьютекс/lock на (userId, date) для защиты от параллельной генерации.

### 3.3 Инвалидация инсайтов при редактировании
**Что:** В обработчиках `PUT /meals` и `DELETE /meals`: после успешной операции вызывать `DailySummaryService.InvalidateAsync(userId, date)`. Frontend: после редактирования/удаления блюда помечать локальный daily summary как устаревший.
**Принятие:** Редактировать блюдо → GET daily-summary возвращает флаг устаревания или запускает пересчёт; старые инсайты не показываются после правки.

### 3.4 Система toast-уведомлений
**Что:** Глобальный toast-компонент в React (справа сверху, автоскрытие 4с, стиль macOS). События: `InsightsReady`, `PatternAlert`, `StreakAlert`. Toast context предоставляет `showToast(type, message)`. После загрузки DailySummary впервые за сегодня → показать "Инсайты дня готовы".
**Принятие:** `showToast('InsightsReady', '...')` рендерит toast справа сверху; скрывается через 4с; несколько toast'ов стекируются.

### 3.5 Frontend: вкладка "День"
**Что:** Кольцо калорий (потреблено / цель), полосы БЖУ, список блюд по времени (каждая карточка: название, калории, БЖУ, кнопки редактировать/удалить), секция инсайтов DailySummary (скелетон во время генерации), FAB "+". Если профиль не заполнен: жёлтый persistent баннер "Заполни профиль для персонализированных инсайтов" со ссылкой.
**Принятие:** Корректный рендер с 0 блюдами (empty state); с блюдами; секция инсайтов показывает скелетон затем контент; баннер-нотификация появляется при незаполненном профиле.

## Блок 4: Профиль и цели

### 4.1 Profile API
**Что:** Добавить поля профиля к `User`: `WeightKg`, `HeightCm`, `Age`, `Sex`, `DietType`, `FeedbackTone`, `PreferredLanguage`, `ProfileCompletedAt`. `GET /profile`, `PUT /profile`. `ProfileCompletedAt` устанавливается при заполнении всех обязательных полей.
**Принятие:** PUT с полным профилем устанавливает `ProfileCompletedAt`; GET возвращает обновлённые поля; частичный PUT не устанавливает `ProfileCompletedAt`.

### 4.2 Goals API
**Что:** Создать `UserGoal`: `UserId`, `GoalType` (enum: Cut/Maintain/Bulk), `DailyCalorieTarget`, `ProteinTargetG` (nullable), `FatTargetG` (nullable), `CarbsTargetG` (nullable), `ActiveSince`. `GET /goals`, `PUT /goals`.
**Принятие:** PUT создаёт или обновляет цель; GET возвращает текущую; кольцо калорий в Day tab использует цель если она задана.

### 4.3 Frontend: вкладка "Профиль"
**Что:** Вкладка с формой: вес, рост, возраст, пол (select), тип цели (radio), тип диеты (select), тон фидбэка (radio: нейтральный/прямой/жёсткий), язык (select). Кнопка сохранить. Индикатор заполненности ("Профиль 3/7 полей"). Ссылка на раздел целей.
**Принятие:** Форма сохраняется в API; индикатор обновляется; смена языка сохраняется в localStorage и влияет на заголовок языка AI.

### 4.4 Ветвление анонимного режима в агентах
**Что:** В `DailySummaryAgent`, `WeeklyPatternAgent`, `MealFeedbackAgent`: проверять наличие `ProfileCompletedAt`. Если null — общий анализ (без персонализированных целей). Если установлен — персонализированный с профилем + целями.
**Принятие:** Unit-тест: одинаковые блюда с профилем и без → разный текст инсайтов; null reference ошибок нет ни в одном из путей.

## Блок 5: Недельная аналитика и календарь

### 5.1 WeeklyReport entity + API
**Что:** Создать `WeeklyReport`: `UserId`, `WeekStartDate` (понедельник), `Patterns` (JSON), `CalendarDayStatuses` (JSON: дата → `green`/`yellow`/`red`), `GeneratedAt`. `GET /weekly-report?weekStart=` — возвращает отчёт или запускает генерацию. `POST /weekly-report/invalidate?weekStart=`.
**Принятие:** GET возвращает 404 до логирования блюд на неделе; отчёт после генерации; инвалидация сбрасывает флаг.

### 5.2 WeeklyPatternAgent
**Что:** Реализовать `WeeklyPatternAgent` (Level 2, LLM). Вход: 7 DailySummaries + профиль/цели. Выход: массив паттернов + карта `CalendarDayStatuses`. Логика статусов: green = в пределах 10% от цели; yellow = 10–25% превышения; red = >25%.
**Принятие:** Интеграционный тест: 7 дней блюд → непустой массив паттернов; карта статусов с записью для каждого дня с данными.

### 5.3 Frontend: вкладка "Неделя"
**Что:** Сводные полосы калорий/БЖУ за неделю, список инсайтов паттернов (lazy с скелетоном), календарная сетка (7 столбцов × N недель, каждая ячейка закрашена по статусу). Тап по ячейке дня — навигация на Day view для этого дня. Toast при первой генерации недельного отчёта.
**Принятие:** Календарь рендерится с правильными цветами по данным API; тап по дню навигирует корректно; скелетон во время генерации.

## Блок 6: Pattern Breaker

### 6.1 PatternEvent entity + API
**Что:** Создать `PatternEvent`: `UserId`, `PatternKey` (строковый enum), `Type` (Positive/Warning), `TriggeredAt`, `Acknowledged` (bool), `Message`. `GET /pattern-events?limit=20` (последние, непрочитанные первыми). `POST /pattern-events/{id}/acknowledge`.
**Принятие:** GET возвращает события по убыванию triggered_at; acknowledge устанавливает флаг; подтверждённые события идут последними.

### 6.2 PatternBreakerAgent + встроенные паттерны
**Что:** Реализовать `PatternBreakerAgent`. Запускается после каждого сохранения блюда и после генерации DailySummary. Проверяет 9 встроенных паттернов по истории последних 30 дней. Создаёт `PatternEvent` при выполнении условий. Rate-limit: один `PatternKey` не более одного раза в 3 дня на пользователя.
**Принятие:** Unit-тест для каждого паттерна: история срабатывания → событие создано; история без срабатывания → событие не создано; rate-limit: два срабатывания за 3 дня → второе событие не создаётся.

### 6.3 Ввод привычек пользователя
**Что:** Таблица `UserHabits`: `UserId`, `HabitDescription` (текст), `CreatedAt`. `POST /habits`, `GET /habits`, `DELETE /habits/{id}`. В Profile tab: раздел "Мои привычки" со списком + поле "Добавить привычку". Привычки передаются как контекст в промпты `DailySummaryAgent` и `PatternBreakerAgent`.
**Принятие:** Привычка сохранена через API; отображается в Profile tab; текст привычки присутствует в LLM-промпте (проверить по логу).

### 6.4 Frontend: алерты и лента Pattern Breaker
**Что:** Toast-уведомления для новых `PatternEvent` (проверка при фокусе приложения / после сохранения блюда). Вкладка "Аналитика" включает секцию "Pattern Breaker": список последних событий (иконка по типу, сообщение, дата, кнопка подтвердить).
**Принятие:** Новое warning-событие → toast в течение 5с после сохранения блюда; positive-событие → другая иконка/цвет; лента показывает все последние события; кнопка подтверждения работает.

## Блок 7: Месячная стратегия и вкладка аналитики

### 7.1 MonthlyStrategyAgent
**Что:** Реализовать `MonthlyStrategyAgent` (Level 2, LLM). Вход: последние 4 WeeklyReport + профиль/цели. Выход: стратегическая оценка (3–5 строк) + объект прогноза (`estimatedWeightChangePer30Days`, `deficitConsistencyPercent`, `mainBlocker`). Lazy-триггер при первом открытии вкладки "Аналитика" за текущий месяц.
**Принятие:** Интеграционный тест: 4 недели данных → непустая оценка; объект прогноза с корректными числовыми полями.

### 7.2 Расчёт прогноза
**Что:** Реализовать `ForecastService`: по среднему суточному отклонению калорий от цели за последние 30 дней вычислить предполагаемое изменение веса (7700 ккал ≈ 1 кг). Возвращает `ForecastResult` для `MonthlyStrategyAgent` (как контекст) и для вкладки аналитики напрямую.
**Принятие:** Unit-тест: дефицит 500 ккал/день × 30 дней → ~1.9 кг потери; профицит → положительное число.
**Примечания:** Чистая арифметика — LLM не нужен.

### 7.3 Frontend: вкладка "Аналитика и рекомендации"
**Что:** Секции вкладки: (1) Месячная стратегия — lazy-загрузка с скелетоном + метка "сгенерировано"; (2) Карточка прогноза — "При текущем темпе: ±X кг/месяц"; (3) Лента Pattern Breaker (из Блока 6). Toast при первой генерации месячного отчёта.
**Принятие:** Все три секции рендерятся; карточка прогноза показывает правильный знак (+/-); скелетон при генерации; toast срабатывает один раз в месяц на пользователя.

## Блок 8: Полировка и готовность к продакшену

### 8.1 Loading, error и empty states
**Что:** Аудит всех экранов. Реализовать: скелетон-лоадеры для всех асинхронных данных, баннеры ошибок с кнопкой повтора, empty states с CTA для: нет блюд сегодня, нет данных за неделю, нет событий паттернов, профиль не заполнен (полноэкранный промпт при первом запуске).
**Принятие:** Симуляция сетевой ошибки → баннер с кнопкой повтора; симуляция отсутствия данных → empty state с CTA; нигде нет белых пустых экранов.

### 8.2 Валидация данных (frontend + backend)
**Что:** Frontend: валидация форм профиля и текстового ввода еды (обязательные поля, числовые диапазоны). Backend: FluentValidation на всех POST/PUT endpoint'ах. Структурированные ответы `400` с ошибками по полям.
**Принятие:** Отправить пустую форму профиля → inline-ошибки по полям; невалидный payload в API → 400 с объектом `errors`; валидный payload проходит.

### 8.3 Абстракция хранилища
**Что:** Определить `IFileStorage` в Application: `Task<string> SaveTemporaryAsync(byte[] data, string ext)`, `Task DeleteAsync(string key)`. Реализовать `LocalFileStorage` для dev. Всё взаимодействие с файлами через интерфейс — никаких прямых `System.IO` вне Infrastructure.
**Принятие:** Замена `LocalFileStorage` на stub-реализацию → все тесты, зависящие от фото, проходят.

### 8.4 Конфигурация деплоя
**Что:** `docker-compose.yml` с сервисами: `api` (ASP.NET Core), `db` (PostgreSQL), `client` (Nginx с собранным React). `Dockerfile` для API и клиента. Конфиг через env: строка подключения БД, JWT secret, ключ API модели, путь хранилища. README с инструкцией по локальному запуску.
**Принятие:** `docker compose up` → приложение доступно на `localhost:3000`; вход работает; загрузка фото работает.
