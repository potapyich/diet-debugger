# План: Diet Debugger

## Архитектура

```
┌─────────────────────────────────────────┐
│           React + Vite SPA              │
│  День | Неделя | Аналитика | Профиль    │
└──────────────┬──────────────────────────┘
               │ REST API (JSON)
┌──────────────▼──────────────────────────┐
│         ASP.NET Core API                │
│  ┌─────────────┐  ┌──────────────────┐  │
│  │ Controllers │  │  Фоновые задачи  │  │
│  └──────┬──────┘  └────────┬─────────┘  │
│         │                  │            │
│  ┌──────▼──────────────────▼─────────┐  │
│  │       AI Agent Pipeline           │  │
│  │  Vision | Feedback | Summary |    │  │
│  │  Weekly | Monthly | PatternBreak  │  │
│  └──────────────────────────────────┘  │
└──────────────┬──────────────────────────┘
               │
┌──────────────▼──────────────────────────┐
│            PostgreSQL                   │
└─────────────────────────────────────────┘
```

**Ключевые принципы:**
- AI-агенты за интерфейсами — модель можно менять
- Level 1 агенты работают синхронно в рамках запроса (<2с)
- Level 2 агенты — асинхронно, запускаются lazy при открытии экрана или по расписанию
- Фото временные; хранятся только структурированные данные

---

## Блоки работ

### Блок 1: Фундамент
**Что:** Рабочий скелет — API, БД, авторизация, модель пользователя
**Почему первый:** Всё остальное зависит от этого. Без рабочего бэкенда и контекста пользователя нет ни одной фичи.
**Включает:**
- Структура solution (слои API, Domain, Infrastructure, Application)
- PostgreSQL + EF Core, начальные миграции
- Сущность User + поля профиля
- Авторизация email/пароль с JWT (регистрация, вход, refresh)
- Health check endpoint
- Scaffold React + Vite, роутинг, auth context, защищённые роуты
**Зависимости:** нет

---

### Блок 2: Ядро логирования еды
**Что:** Полный цикл добавления приёма пищи — ввод (фото/текст) → AI-анализ → подтверждение пользователем → сохранение
**Почему второй:** Основная ценность продукта. Вся аналитика и паттерны требуют данных о приёмах пищи.
**Включает:**
- Сущность `Meal` + CRUD API
- Интерфейс `FoodVisionAgent` + реализация (фото → данные; текст → данные)
- Async-флоу: загрузка → поллинг результата (или SSE)
- Обработка низкой уверенности — ветка UX "мы не уверены"
- Редактирование пользователем до сохранения
- `MealFeedbackAgent` (Level 1, rule-based) — 1–2 мгновенных инсайта после сохранения
- Frontend: bottom sheet "+", флоу камера/галерея/текст, экран результата, экран редактирования
**Зависимости:** Блок 1

---

### Блок 3: Экран дня
**Что:** Полная вкладка "День" — приёмы пищи, текущие итоги, сравнение с целью, инсайты дня
**Почему третий:** Первое что видит пользователь после логирования; необходим для базового цикла удержания.
**Включает:**
- Экран состояния дня (калории / цель, кольца БЖУ, список приёмов)
- `DailySummaryAgent` (Level 2 async) — запускается при первом открытии аналитики дня
- Инвалидация инсайтов при редактировании/удалении приёма → пересчёт при следующем открытии
- Система toast-уведомлений (справа сверху) — триггер "инсайты готовы"
- Плашка-напоминание заполнить профиль (persistent, если профиль не заполнен)
**Зависимости:** Блок 2

---

### Блок 4: Профиль и цели
**Что:** Профиль пользователя, цели, настройки
**Почему четвёртый:** Разблокирует персонализированный анализ во всех Level 2 агентах. Пользователь может пропустить, но без профиля нет полной ценности.
**Включает:**
- API профиля (вес, рост, возраст, пол, цель, тип диеты, тон фидбэка, язык)
- API целей (дневной лимит калорий, опциональные цели по БЖУ)
- Экран профиля (frontend)
- Обработка анонимного режима — разветвление общего vs персонализированного анализа в агентах
**Зависимости:** Блок 1

---

### Блок 5: Недельная аналитика и календарь
**Что:** Вкладка "Неделя" — паттерны, календарная сетка, недельный отчёт
**Почему пятый:** Второй по важности аналитический слой; нужны данные за несколько дней.
**Включает:**
- `WeeklyPatternAgent` (Level 2 async) — запускается при первом открытии вкладки "Неделя"
- Сущность `WeeklyReport` + API
- Frontend вкладки "Неделя" (сводная статистика, инсайты паттернов, календарная сетка)
- Календарная сетка: цветовой статус каждого дня (зелёный / жёлтый / красный) на основе DailySummary
- Lazy-генерация + toast-уведомление когда готово
**Зависимости:** Блок 3 (DailySummary нужен для цветов календаря)

---

### Блок 6: Pattern Breaker
**Что:** Детектирование поведенческих паттернов — алерты и позитивное подкрепление
**Почему шестой:** Нужна история приёмов и дней для осмысленного срабатывания паттернов.
**Включает:**
- Сущность `PatternEvent` + API
- `PatternBreakerAgent` — запускается после каждого сохранения приёма и генерации DailySummary
- Библиотека встроенных паттернов (9 паттернов из PRD)
- Ввод пользовательских привычек (раздел профиля)
- UI алертов: toast-уведомления + лента Pattern Breaker во вкладке "Аналитика"
**Зависимости:** Блоки 3, 4

---

### Блок 7: Месячная стратегия и вкладка аналитики
**Что:** Вкладка "Аналитика и рекомендации" — месячная стратегия, лента Pattern Breaker, прогноз
**Почему седьмой:** Требует данных за неделю+; имеет смысл после стабилизации недельного слоя.
**Включает:**
- `MonthlyStrategyAgent` (Level 2 async)
- Frontend вкладки "Аналитика и рекомендации"
- Раздел прогноза ("при текущем темпе: -X кг/месяц")
- Лента истории Pattern Breaker
**Зависимости:** Блоки 5, 6

---

### Блок 8: Полировка и готовность к продакшену
**Что:** Обработка ошибок, пустые состояния, загрузочные состояния, деплой
**Почему последний:** Полировка поверх работающих фич.
**Включает:**
- Все loading / error / empty states по всем экранам
- Fallback-сообщения при отсутствии профиля
- Edge cases флоу с низкой уверенностью распознавания
- Обработка ошибок API + понятные сообщения для пользователя
- Валидация данных (frontend + backend)
- Абстракция хранилища (локальное → интерфейс, готовый к облаку)
- Конфиг окружений, пайплайн деплоя
**Зависимости:** Все предыдущие блоки

---

## Логика последовательности

1. **Фундамент первым** — авторизация и БД — основа; без них ничего не строится
2. **Логирование еды раньше аналитики** — аналитика без данных бессмысленна; логирование — ядро петли удержания
3. **День раньше профиля** — пользователь должен сразу увидеть ценность; профиль углубляет ценность, но не является воротами
4. **Неделя раньше Pattern Breaker** — паттерны нуждаются в агрегированной истории (DailySummary) для корректного срабатывания
5. **Месяц последним** — наименьшая частота, требует больше всего данных, самые высокие LLM-затраты — сначала валидируем более дешёвые слои
6. **Полировка последней** — не полировать недостроенные фичи

## Риски и допущения

| Риск | Митигация |
|------|-----------|
| Точность распознавания AI недостаточна для доверия пользователя | Сделать UX коррекции максимально простым; ветка низкой уверенности — полноценный флоу |
| LLM-время ответа для Level 2 агентов слишком долгое | Async + lazy-генерация + toast-уведомление разрывают ожидание и навигацию |
| Стоимость Vision API слишком высока в масштабе | Абстракция за интерфейсом; можно менять модели или добавить слой кэширования |
| Пользователи не заполняют профиль → персонализация не активируется | Persistent UI-нотификация; показать чёткое различие между общим и персонализированным анализом |
| Pattern Breaker срабатывает слишком часто → усталость от алертов | Rate-limit алертов по паттерну; требовать N случаев перед первым триггером |
| Доступ к камере через мобильный браузер | Нативный file input с `capture="camera"`; работает в мобильных браузерах |
